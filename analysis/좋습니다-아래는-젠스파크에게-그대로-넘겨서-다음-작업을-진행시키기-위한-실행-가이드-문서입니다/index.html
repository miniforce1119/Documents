    생성일: 2026-03-08 출처: 외부 AI

    목표는 지금까지 정리된 방향을 제품/기능 설계 문서 수준으로 명확하게 전달하는 것입니다.

    AI 문서화 시스템 실행 가이드

    대상: 젠스파크 구현용 가이드 문서

    1. 프로젝트 개요

    이 프로젝트의 목적은 AI가 생성한 유용한 답변을 문서 자산으로 축적하는 시스템을 만드는 것이다.

    초기에는 사내 Wiki(Confluence)로 직접 변환하는 방향을 검토했지만, AI가 생성한 Markdown과 Wiki 포맷 간의 불일치, 렌더링 문제, 자동화 복잡도 때문에 방향을 조정했다.

    현재 목표는 다음과 같다.

    AI 답변을 Markdown 문서로 정리하고, 이를 GitHub Enterprise + MkDocs 기반 Docs Site에 축적하는 문서화 시스템을 구축한다.

    이 시스템은 단순 저장기가 아니라,

    유용한 AI 결과를 선별하고 정규화하고 발행하는 문서 검토/발행 시스템이어야 한다.

    2. 핵심 철학

    이 시스템에서 가장 중요한 데이터는 AI로부터 생성된 데이터다.

    즉, 문서화 대상의 중심은 다음이다.

    사내 Agent Builder 전용 AI Agent가 생성한 결과

    사외 AI(ChatGPT, Claude 등)가 생성한 결과

    향후에는 기타 텍스트 메모, 외부 설명, 정리된 회의 내용 등도 포함 가능

    핵심 철학은 다음과 같다.

    이 도구는 Markdown 에디터가 아니라,

    AI 생성 지식을 문서 자산으로 변환하는 도구다.

    3. 현재 구현 상태

    현재까지 Streamlit 기반 앱으로 아래 흐름은 이미 구현되었다.

    구현 완료된 흐름

    Agent Builder로부터 나온 결과가 이미 정해진 포맷으로 온다고 가정

    사용자가 그 텍스트를 Streamlit 앱에 붙여넣음

    앱이 이를 파싱함

    .md 파일 생성

    GitHub Pages / MkDocs 반영

    즉 현재 앱은 사내 Agent Builder의 정형화된 결과를 직접 받아 문서화하는 흐름은 구현된 상태다.

    4. 다음 단계 목표

    다음 단계에서는 아래 두 가지 입력 방식을 모두 지원해야 한다.

    Mode A. Direct Import

    사내 Agent Builder 결과를 그대로 받아 처리

    입력 형태 예시:

    TITLE:

    문서 제목

    FILENAME:

    저장용-파일명

    CONTENT:

    문서 제목

    ...

    처리 방식:

    파싱

    Preview

    Inbox 저장 또는 Publish

    Mode B. Reformat via Agent

    사외 AI 결과를 복붙한 뒤, 사내 Agent Builder의 Reformat Agent를 통해 다시 정형화된 문서 포맷으로 재구성

    입력 형태:

    자유 텍스트

    Markdown이 일부 손실된 텍스트

    ChatGPT/Claude 복붙 결과

    plain text

    처리 방식:

    사용자가 외부 AI 결과를 붙여넣음

    앱 또는 내부 흐름이 Reformat Agent로 전달

    Reformat Agent가 사내 표준 문서 포맷으로 재생성

    동일한 Preview / Inbox / Publish 흐름으로 연결

    5. 왜 두 입력 모드를 모두 지원해야 하는가

    이 툴은 더 이상 단순히 Agent Builder 결과 저장기가 아니다.

    실제로는 아래 역할을 수행해야 한다.

    여러 AI 소스에서 나온 유용한 결과를, 사내 표준 문서 형식으로 정규화하여 축적하는 시스템

    따라서 입력 소스가 복수여야 하며, 최종 출력 포맷은 반드시 통일되어야 한다.

    즉 내부 기준 출력은 항상 아래 형태를 유지한다.

    TITLE:

    ...

    FILENAME:

    ...

    CONTENT:

    ...

    이렇게 해야 downstream 로직이 단순해진다.

    Preview 로직 공통 사용

    Inbox 저장 로직 공통 사용

    Publish 로직 공통 사용

    GitHub Enterprise 반영 로직 공통 사용

    6. Agent 설계 방향

    결론

    처음 단계에서는 Agent를 2개로 분리하는 것이 좋다.

    Agent 1. 질문용 Document Writer Agent

    역할:

    사용자의 질문을 받아

    저장 가치가 있는 문서 형태로 새 문서를 생성

    TITLE / FILENAME / CONTENT 구조로 출력

    입력 예:

    MkDocs와 GitHub Actions를 이용한 문서 자동화 workflow를 설명해줘

    역할 특성:

    새 문서를 쓰는 역할

    설명 확장

    배경/예시/결론 포함

    완성형 Markdown 문서 생성

    Agent 2. Reformat Agent

    역할:

    사외 AI 결과나 자유형 텍스트를 입력받아

    사내 표준 문서 포맷 Markdown으로 재구성

    TITLE / FILENAME / CONTENT 구조로 출력

    입력 예:

    외부 AI 복붙 텍스트

    역할 특성:

    원문 의미를 최대한 보존

    구조화

    제목/파일명 재설정

    Markdown 문서 포맷으로 재작성

    왜 2개로 분리해야 하는가

    한 개 Agent로 합치면 아래 문제가 생길 수 있다.

    입력이 질문인지 재구성 대상 텍스트인지 모호해짐

    문서 생성과 문서 재정리 역할이 섞여 품질 흔들림

    디버깅 어려움

    프롬프트 설계가 복잡해짐

    따라서 초기에 2개로 나누고, 나중에 충분히 안정화되면 통합 여부를 판단하는 것이 좋다.

    7. UX 방향

    시스템은 반드시 문서 생성과 저장을 분리해야 한다.

    이유:

    AI 결과는 모두 저장 가치가 있는 것이 아니기 때문이다.

    가장 중요한 UX는 다음이다.

    Generate / Import

    ↓

    Preview

    ↓

    Decide

    - Save to Inbox

    - Publish

    - Drop

    즉 “바로 저장”보다 “검토 후 저장”이 핵심이다.

    10. 저장소 및 발행 구조

    최종 발행 대상은 GitHub Enterprise + MkDocs 기반 Docs Site다.

    저장소 구조 예시

    repo-root/

    ├─ mkdocs.yml

    ├─ docs/

    │ ├─ index.md

    │ ├─ analysis/

    │ ├─ guides/

    │ ├─ reports/

    │ └─ concepts/

    ├─ inbox/

    └─ published/

    또는 로컬 앱 내부 저장 구조와 배포 저장 구조를 분리해도 된다.

    발행 흐름

    Save to Inbox

    ↓

    Review

    ↓

    Publish

    ↓

    docs//.md 저장

    ↓

    Git add / commit / push

    ↓

    GitHub Actions

    ↓

    MkDocs build

    ↓

    Private Docs Site 반영

    11. GitHub Enterprise 사용 이유

    GitHub Enterprise를 사용하므로 다음이 가능하다.

    문서를 클라우드에 저장

    private 문서 사이트 운영 가능

    Git history 기반 버전관리 가능

    문서 자산 축적 가능

    즉 이 시스템은 Confluence를 직접 대체하려는 것이 아니라,

    AI 친화적인 private Docs-as-Code 문서 시스템

    으로 보는 것이 맞다.

    12. 중요한 처리 원칙

    원칙 1. 모든 입력은 최종적으로 표준 포맷으로 정규화

    아래 포맷은 내부 표준 출력이다.

    TITLE:

    ...

    FILENAME:

    ...

    CONTENT:

    ...

    원칙 2. 입력이 Markdown이 아니어도 수용

    외부 AI 복붙 결과는 Markdown 형태를 잃을 수 있다.

    하지만 이것은 문제라기보다 정상 입력 유형으로 간주해야 한다.

    중요한 것은:

    원래 Markdown을 100% 복원하는 것보다

    문서화 가능한 Markdown 구조로 재구성하는 것이다.

    원칙 3. 저장 전 반드시 Preview

    저장 전 확인은 필수다.

    이 단계에서 사용자는:

    문서 가치 판단

    제목 수정

    카테고리 선택

    저장 여부 결정

    을 할 수 있어야 한다.

    13. 젠스파크가 다음 단계에서 진행해야 할 내용

    젠스파크는 다음 기능 요구사항을 기준으로 다음 작업을 진행하면 된다.

    1. 입력 모드 2개 지원

    Agent Builder Direct Import

    External AI → Reformat via Agent

    2. 공통 출력 포맷 유지

    TITLE

    FILENAME

    CONTENT

    3. Inbox / Review / Publish 흐름 유지

    바로 docs로 저장하지 말고 중간 검토 단계 유지

    4. Preview UX 강화

    Markdown 문서 미리보기

    최종 렌더링 확인

    metadata 확인

    5. Publish 흐름 공통화

    어떤 입력 모드든 최종적으로 동일한 발행 로직을 사용

    14. 권장 개발 순서

    15. 최종 정의

    이 시스템은 아래처럼 정의한다.

    AI 결과를 복사해 저장하는 툴이 아니라,

    여러 AI 소스에서 나온 유용한 지식을 사내 표준 문서로 정규화하고 발행하는 문서 검토/발행 시스템

    즉 목표는 다음이다.

    AI 결과 수집

    ↓

    정규화

    ↓

    검토

    ↓

    발행

    ↓

    지식 자산 축적

    16. 젠스파크에게 전달할 한 줄 요약

    아래 문장을 핵심 요청사항으로 전달하면 된다.

    현재 구현된 Agent Builder formatted direct import 흐름은 유지하고, 여기에 외부 AI 복붙 텍스트를 사내 Reformat Agent를 통해 표준 Markdown 문서 포맷으로 재구성한 뒤 동일한 Inbox / Review / Publish 흐름으로 연결하는 2-mode 문서화 시스템으로 확장하고 싶다.

    원하시면 다음 단계로 이 문서를 바탕으로 젠스파크에게 바로 붙여넣을 수 있는 짧은 실행 요청 프롬프트 버전까지 정리해드리겠습니다.
